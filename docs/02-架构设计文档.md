## 1 引言

### 1.1 编写目的

本文档在《01-需求文档》的基础上，说明系统如何实现：划分模块、设计类与接口、确定关键数据结构、描述对象间的协作流程，并记录主要设计决策的取舍理由。本文档是编码的直接依据，也是《03-技术文档》与答辩说明的基础。

### 1.2 设计范围

覆盖节点抽象、发布者、订阅者、消息、核心管理模块五部分，以及异常体系、日志规范、目录结构与构建方式。不涉及网络通信、多线程调度与持久化存储（后者列为可扩展项）。

### 1.3 设计原则

| 原则 | 在本项目中的体现 |
|---|---|
| 单一职责 | 节点只负责自身行为，消息只负责数据承载，核心只负责映射与转发 |
| 依赖抽象 | 核心模块只持有 `Node*`，不感知 `Publisher` / `Subscriber` 的具体行为 |
| 开闭原则 | 新增节点类型时，核心模块代码无需修改 |
| 封装与只读 | 名称、话题、消息内容、时间戳一律私有 + 只读访问，杜绝外部篡改 |
| RAII 与明确所有权 | 节点由调用方创建并拥有，核心模块仅"借用"指针 |
| 失败显式化 | 非法输入一律抛异常，不用返回码，不静默忽略 |

## 2 总体架构

### 2.1 分层结构

```
┌──────────────────────────────────────────────────────────────┐
│  应用层      main.cpp（演示程序） / tests（测试程序）          │
│              创建节点、驱动发布、捕获异常、展示日志             │
├──────────────────────────────────────────────────────────────┤
│  节点层      Node（抽象） ← Publisher / Subscriber            │
│              承担生命周期（init / shutdown）与业务动作          │
├──────────────────────────────────────────────────────────────┤
│  核心层      ROS（单例）                                       │
│              话题映射、节点注册、消息转发、统一关闭             │
├──────────────────────────────────────────────────────────────┤
│  基础设施    Message（数据载体） / Exception（异常体系）        │
│              Logger（日志） / Util（字符串处理）                │
└──────────────────────────────────────────────────────────────┘
```

**依赖方向**：上层依赖下层，下层不反向依赖上层。核心层不包含任何 `main` 或测试代码，因此可被独立测试。

### 2.2 构建产物划分

| CMake 目标 | 类型 | 内容 | 用途 |
|---|---|---|---|
| `rosmini_core` | 静态库 | `Node` / `Publisher` / `Subscriber` / `Message` / `ROS` / `Exception` / `Logger` | 被界面、演示与测试共同链接 |
| `rosmini_demo` | 图形程序（WIN32） | `src/main.cpp` + `src/GuiApp.cpp` | 交互式界面，答辩演示 |
| `rosmini_batch` | 控制台程序 | `src/batch_main.cpp` | 一次性输出全部日志，便于截图与命令行验证 |
| `rosmini_tests` | 控制台程序 | `tests/*.cpp` | 结构化测试用例，覆盖正常/边界/异常 |

> 这样切分的目的：**核心逻辑不依赖 `main`**，测试可以直接构造节点并断言，不需要启动整个演示流程（对应 NFR-04）。

### 2.3 命名空间

所有类型置于 `namespace rosmini` 中。原因：本机后续比赛会使用真实 ROS（其命名空间为 `ros`），若把类命名为全局 `ROS`、`Node`，将来同工程混用极易冲突。命名空间隔离是一种低成本的预防措施。

## 3 类设计

### 3.1 类图

```
                        ┌───────────────────────────────┐
                        │            Node               │  «abstract»
                        ├───────────────────────────────┤
                        │ # name_ : std::string         │
                        ├───────────────────────────────┤
                        │ + Node(name : string)         │
                        │ + name() : const string&      │
                        │ + init() : void = 0           │
                        │ + shutdown() : void = 0       │
                        │ + ~Node() virtual             │
                        └───────────────△───────────────┘
                                        │ 继承
                    ┌───────────────────┴───────────────────┐
                    │                                       │
      ┌─────────────────────────────┐       ┌─────────────────────────────┐
      │         Publisher           │       │         Subscriber          │
      ├─────────────────────────────┤       ├─────────────────────────────┤
      │ - topic_ : std::string      │       │ - topic_ : std::string      │
      ├─────────────────────────────┤       ├─────────────────────────────┤
      │ + Publisher(name, topic)    │       │ + Subscriber(name, topic)   │
      │ + topic() : const string&   │       │ + topic() : const string&   │
      │ + init() override           │       │ + init() override           │
      │ + shutdown() override       │       │ + shutdown() override       │
      │ + publish(data : string)    │       │ + receive(msg : const       │
      │                             │       │             Message&)       │
      └──────────────┬──────────────┘       └──────────────△──────────────┘
                     │ 转发                                │ 推送
                     ▼                                     │
      ┌──────────────────────────────────────────────────────────────┐
      │                        ROS  «singleton»                      │
      ├──────────────────────────────────────────────────────────────┤
      │ - publishers_  : unordered_map<string, vector<Publisher*>>   │
      │ - subscribers_ : unordered_map<string, vector<Subscriber*>>  │
      │ - nodes_       : vector<Node*>          （用于统一关闭）      │
      ├──────────────────────────────────────────────────────────────┤
      │ + static instance() : ROS&                                   │
      │ + registerPublisher(p : Publisher*)                          │
      │ + registerSubscriber(s : Subscriber*)                        │
      │ + unregister(node : Node*)                                   │
      │ + publish(topic : const string&, msg : const Message&)       │
      │ + shutdownAll()                                              │
      └──────────────────────────────────────────────────────────────┘

      ┌───────────────────────────┐        ┌───────────────────────────┐
      │         Message           │        │  std::runtime_error       │
      ├───────────────────────────┤        └────────────△──────────────┘
      │ - content_   : string     │                     │
      │ - timestamp_ : string     │              RosException
      ├───────────────────────────┤              ┌──────┴───────┐
      │ + Message(content)        │      NodeException  TopicException
      │ + content()   : const &   │                     │
      │ + timestamp() : const &   │             MessageException
      └───────────────────────────┘
```

图例：`+` 公有、`#` 保护、`-` 私有；`△` 表示继承/实现关系。

### 3.2 各类职责

| 类 | 职责 | 不负责 |
|---|---|---|
| `Node` | 封装节点名称、定义生命周期接口、约束子类必须实现 `init` / `shutdown` | 不关心具体通信行为，不知道话题存在 |
| `Publisher` | 持有话题名；初始化时注册；接收字符串并封装为消息；委托核心转发 | 不关心谁订阅、有多少订阅者 |
| `Subscriber` | 持有话题名；初始化时注册；被动接收消息并输出日志 | 不主动拉取消息，不决定何时接收 |
| `Message` | 承载业务内容；构造时生成时间戳；对外只读 | 不关心话题，不关心投递 |
| `ROS` | 维护话题映射、注册与反注册、按话题转发、统一关闭 | 不创建节点，不拥有节点生命周期 |
| `RosException` 及子类 | 携带分类明确的错误语义 | 不负责输出日志（由捕获方决定） |

### 3.3 接口定义（设计级）

以下为类声明草案，`src/*.cpp` 的实现须与此保持一致。

```cpp
// include/rosmini/Node.h
namespace rosmini {

class Node {
public:
    explicit Node(std::string name);
    virtual ~Node() = default;

    const std::string& name() const noexcept;   // 只读访问，符合 FR-02

    virtual void init() = 0;        // 初始化：注册 + 日志
    virtual void shutdown() = 0;    // 关闭：日志（+ 反注册）

protected:
    std::string name_;
};

} // namespace rosmini
```

```cpp
// include/rosmini/Publisher.h
namespace rosmini {

class Publisher : public Node {
public:
    Publisher(std::string name, std::string topic);

    const std::string& topic() const noexcept;

    void init() override;
    void shutdown() override;

    // 接收传感器字符串 → 创建 Message → 转发至核心
    void publish(const std::string& sensorData);

private:
    std::string topic_;
};

} // namespace rosmini
```

```cpp
// include/rosmini/Subscriber.h
namespace rosmini {

class Subscriber : public Node {
public:
    Subscriber(std::string name, std::string topic);

    const std::string& topic() const noexcept;

    void init() override;
    void shutdown() override;

    // 由核心模块调用，完成被动接收
    void receive(const Message& msg);

private:
    std::string topic_;
};

} // namespace rosmini
```

```cpp
// include/rosmini/Message.h
namespace rosmini {

class Message {
public:
    explicit Message(std::string content);   // 内部自动生成时间戳

    const std::string& content() const noexcept;
    const std::string& timestamp() const noexcept;

private:
    std::string content_;
    std::string timestamp_;
};

} // namespace rosmini
```

```cpp
// include/rosmini/ROS.h
namespace rosmini {

class ROS {
public:
    static ROS& instance();                  // Meyers 单例

    ROS(const ROS&) = delete;
    ROS& operator=(const ROS&) = delete;

    void registerPublisher(Publisher* p);
    void registerSubscriber(Subscriber* s);
    void unregister(Node* node);

    void publish(const std::string& topic, const Message& msg);
    void shutdownAll();

    // 查询接口（供界面与测试使用）
    std::size_t publisherCount(const std::string& topic) const;
    std::size_t subscriberCount(const std::string& topic) const;
    std::size_t nodeCount() const;
    std::vector<std::string> topics() const;

private:
    ROS() = default;

    std::unordered_map<std::string, std::vector<Publisher*>>  publishers_;
    std::unordered_map<std::string, std::vector<Subscriber*>> subscribers_;
    std::vector<Node*> nodes_;
};

} // namespace rosmini
```

### 3.4 设计取舍说明

**为什么 `Publisher` / `Subscriber` 都继承 `Node`？**
核心模块需要统一关闭所有节点（`shutdownAll`），若没有公共基类，就得为核心模块维护两份容器、写两套遍历逻辑，且新增第三种节点时还要再改核心。继承后 `nodes_` 是 `vector<Node*>`，遍历调用虚函数即可——这是**多态**在项目里最实在的用处，而不是为了“看起来面向对象”。

**为什么核心模块存裸指针，不用 `unique_ptr`？**
节点是**由调用方创建**的局部对象（演示程序中是 `main` 的栈对象，测试中也是栈对象）。若核心用 `unique_ptr` 接管所有权，就意味着“核心负责销毁节点”，与“谁创建谁销毁”的语义冲突，栈对象也无法交给 `unique_ptr`。因此选择裸指针 + **析构时自动反注册**的方式来规避悬空指针（见 6.4）。

## 4 关键数据结构

### 4.1 两张映射表

```cpp
std::unordered_map<std::string, std::vector<Publisher*>>  publishers_;
std::unordered_map<std::string, std::vector<Subscriber*>> subscribers_;
```

| 结构 | 用途 | 时间复杂度 |
|---|---|---|
| `publishers_[topic]` | 记录某话题有哪些发布者（用于查询、调试、关闭） | 平均 O(1) 查表，O(k) 遍历 |
| `subscribers_[topic]` | 转发时按话题取出全部订阅者 | 平均 O(1) 查表，O(k) 遍历 |

**为什么用“话题 → 列表”而不是“话题 → 单个节点”？**
需求 FR-11 要求多对多：一个话题可以有多个发布者，也可以有多个订阅者。单个节点无法表达，必须是列表。

**为什么用 `unordered_map` 而不是 `map`？**
本场景只需按话题名精确查找，不需要有序遍历，哈希表平均 O(1) 优于红黑树 O(log n)。项目规模小，两者差异可以忽略，但选哈希表在语义上更贴合“字典/映射表”的用途。

### 4.2 节点总表

```cpp
std::vector<Node*> nodes_;
```

仅用于 `shutdownAll()` 遍历，与两张映射表互补：映射表回答“某话题下有谁”，总表回答“一共有谁”。关闭时以总表为准，可避免同一节点因注册在多个话题下而被关闭多次（对应需求 3.4）。

## 5 关键流程

### 5.1 初始化与注册

```
调用方            Publisher           ROS(单例)
  │                  │                   │
  │ init()           │                   │
  ├─────────────────>│                   │
  │                  │ 输出日志           │
  │                  │ registerPublisher │
  │                  ├──────────────────>│
  │                  │                   │ 1. 校验 topic 非空
  │                  │                   │ 2. 校验节点名未重复
  │                  │                   │ 3. publishers_[topic].push_back(this)
  │                  │                   │ 4. nodes_.push_back(this)
  │                  │<──────────────────┤
  │<─────────────────┤                   │
```

**校验顺序的用意**：先校验再修改，保证任何一次失败的注册都不会污染映射表（强异常安全）。

### 5.2 发布与转发（核心链路）

```
 main        Publisher        ROS           SubscriberA     SubscriberB
  │             │              │                │               │
  │ publish("temperature=25.3")│                │               │
  ├────────────>│              │                │               │
  │             │ 1. 校验内容非空                │               │
  │             │ 2. Message msg(data)  ← 自动生成时间戳         │
  │             │ 3. 输出发布日志                │               │
  │             │ publish(topic,msg)             │               │
  │             ├─────────────>│                │               │
  │             │              │ 4. 查 subscribers_[topic]       │
  │             │              │ 5. 为空 → 抛 TopicException     │
  │             │              │ 6. 遍历                  │               │
  │             │              ├────────────────>│ receive(msg)  │
  │             │              │                │ 输出接收日志   │
  │             │              ├────────────────┼──────────────>│ receive(msg)
  │             │<─────────────┤                │               │
  │<────────────┤ 返回（不等待、无返回值）        │               │
```

**关键点**：第 6 步是**循环**，循环次数等于该话题的订阅者数量；发布者在第 7 步直接返回，中间不涉及任何“等待订阅者响应”的动作。这就是需求里“异步通信”的实际含义——**发布者与订阅者通过核心解耦，发布者不知道也不需要知道订阅者是否存在**。

### 5.3 全局关闭

```
调用方            ROS                    Node(虚函数入口)
  │                │                            │
  │ shutdownAll()  │                            │
  ├───────────────>│                            │
  │                │ 输出全局关闭日志            │
  │                │ for (node : nodes_)        │
  │                ├───────────────────────────>│ node->shutdown()
  │                │                            │  ├ Publisher：输出关闭日志
  │                │                            │  └ Subscriber：输出关闭日志
  │                │ 清空 publishers_/subscribers_/nodes_
  │<───────────────┤                            │
```

**注意**：清空三张表必须在遍历**之后**，否则遍历过程中容器被修改会导致迭代器失效（未定义行为）。这是新手最容易写出的崩溃点。

## 6 异常与生命周期设计

### 6.1 异常体系

```
std::exception
  └── std::runtime_error
        └── rosmini::RosException          // 项目异常基类，统一前缀
              ├── rosmini::NodeException    // 节点名、重复注册、关闭后使用
              ├── rosmini::TopicException   // 话题名为空、话题不存在
              └── rosmini::MessageException // 消息内容为空
```

继承 `std::runtime_error` 的收益：

1. 可直接被 `catch (const std::exception&)` 兜底，不会漏接；
2. `what()` 直接返回构造时传入的中文描述，日志里 `e.what()` 一行就能打印出可读信息；
3. 分类明确后，调用方可以选择只处理某一类（如只捕获 `TopicException`）。

### 6.2 抛出与捕获的位置

| 场景 | 抛出位置 | 捕获位置 |
|---|---|---|
| 空节点名 / 空话题名 | 构造函数 | 调用方（`main` / 测试） |
| 重复节点注册 | `ROS::registerPublisher` / `registerSubscriber` | 调用方 |
| 空消息内容 | `Message` 构造函数 | 调用方 |
| 话题不存在 | `ROS::publish` | 调用方 |
| 关闭后继续通信 | `Publisher::publish` / `Subscriber::receive` | 调用方 |

**设计约束**：核心库内部不允许 `catch` 后吞掉异常（不允许 `catch (...) {}` 空实现），捕获只发生在应用层。这样库的使用者能感知全部错误，不会被静默失败坑害。

### 6.3 对象状态机

```
   [构造] ──> 未初始化 ──init()──> 已初始化 ──shutdown()──> 已关闭
                 │                    │                      │
                 └─ publish/receive ──┘                      └─ publish/receive
                      抛 NodeException                           抛 NodeException（WARN 日志）
```

实现上用两个布尔成员表达：`initialized_`、`closed_`。二者由 `init()` / `shutdown()` 维护，业务接口入口先校验状态。

### 6.4 悬空指针的防护

风险：节点对象销毁后，`ROS` 的映射表里仍留着它的地址，下次转发就访问野指针。

三重防护：

1. **析构自动反注册**：`Node::~Node()` 中调用 `ROS::instance().unregister(this)`，把该指针从三张表中移除；
2. **接口幂等**：`unregister` 对不存在的节点直接返回，不抛异常（析构函数里抛异常会导致 `std::terminate`）；
3. **文档约束**：用户手册明确“节点生命周期不得短于其注册期”。

> 这一条是答辩最可能被追问的技术点：“你的核心模块存的是裸指针，节点销毁了怎么办？”——答“析构时自动从核心注销，且注销接口幂等”，比答“我用了 shared_ptr”更能说明你想过所有权问题。

## 7 日志规范

统一由 `Logger` 提供，节点与核心不直接调用 `std::cout`。

```
[级别] [时间戳] [节点名/模块] 消息内容
```

示例：

```
[INFO ] [2026-11-11 21:30:05] [pub_temp]  发布者已初始化，话题=sensor
[INFO ] [2026-11-11 21:30:05] [sub_mon ]  订阅者已初始化，话题=sensor
[INFO ] [2026-11-11 21:30:05] [pub_temp]  发布消息 → 话题=sensor 内容="temperature=25.3"
[INFO ] [2026-11-11 21:30:05] [sub_mon ]  接收消息 ← 话题=sensor 内容="temperature=25.3" 时间戳=2026-11-11 21:30:05
[ERROR] [2026-11-11 21:30:06] [ROS     ]  话题不存在："sensor_x"
[INFO ] [2026-11-11 21:30:07] [ROS     ]  开始关闭全部节点（共 4 个）
```

**为什么先封装 Logger**：加分项要求“日志分级 + 写入文件”。若初始就把 `std::cout` 散落在各处，后续改造要改十几个文件；封装后只需在 `Logger` 内部加一个 `std::ofstream` 和一个级别阈值。这是“为变化留接口”的典型例子。

**`include` 与 `src` 分离的理由**：使用者只需 `-I include` 即可引用头文件，无需关心实现文件的位置；同时天然区分“对外接口”与“内部实现”，也便于后续打包为库。

## 9 可扩展性设计

| 扩展需求 | 需要改动的文件 | 不需要改动 |
|---|---|---|
| 新增节点类型（如 `ServiceClient`） | 新增 `ServiceClient.h/.cpp`，继承 `Node` | `ROS`、`Publisher`、`Subscriber` |
| 新增消息类型（如 `SensorMessage`） | 新增 `SensorMessage.h`，可继承 `Message` | 核心转发逻辑（仍以 `const Message&` 接收） |
| 日志写入文件 / 分级 | 仅改 `Logger` | 所有调用方 |
| 运行时动态移除节点 | 新增 `ROS::unregister` 的公开用法与演示 | 类结构 |

这是“依赖抽象”带来的实际收益：核心模块对具体类型一无所知，因此新类型不需要触碰核心代码。

## 11 风险与限制

| 编号 | 风险 | 影响 | 应对 |
|---|---|---|---|
| R1 | 裸指针悬空（节点先析构、核心未注销） | 访问非法内存，崩溃 | 析构自动反注册 + 文档约束（6.4） |
| R2 | 单例析构顺序问题（节点为全局对象时） | 程序退出阶段访问已销毁单例 | 约束节点不得定义为全局/静态对象 |
| R3 | 单线程实现 | 多线程并发发布不安全 | 明示限制；线程安全列为 P2 扩展 |
| R4 | 同步分发 | 订阅者处理慢会拖慢发布者 | 当前场景无耗时逻辑；如需解耦可加消息队列 |
| R5 | 消息仅支持字符串 | 无法表达结构化数据 | P1 扩展 `SensorMessage` |
