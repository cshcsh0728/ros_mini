## 3 代码结构

```
include/rosmini/     对外接口（头文件）
src/                 实现（每个类一个 .cpp，外加演示程序 main.cpp）
tests/               测试程序 + 用例表
```

编译成三个目标：

| 目标 | 类型 | 说明 |
|---|---|---|
| `rosmini_core` | 静态库 | 除 `main.cpp` 外全部实现，被下面两个程序共用 |
| `rosmini_demo` | 可执行 | 演示 6 个场景 |
| `rosmini_tests` | 可执行 | 9 组用例、21 项检查 |

把核心代码打成库，是为了让测试程序能直接链接、无需复制源码，也不必启动演示流程——
这是「可测试性」需求（NFR-04）的落地方式。

## 4 模块实现解析

### 4.1 工具层（Util）

时间戳格式要求严格为 `YYYY-MM-DD HH:MM:SS`，用 `std::put_time` 实现：

```cpp
std::tm localTime{};
#ifdef _MSC_VER
    localtime_s(&localTime, &now);   // MSVC 的安全版本
#else
    localtime_r(&now, &localTime);   // POSIX
#endif
std::ostringstream oss;
oss << std::put_time(&localTime, "%Y-%m-%d %H:%M:%S");
```

**为什么不用 `strftime`**：`strftime` 需要预先分配缓冲区并处理返回值，且 `std::localtime`
非线程安全；`put_time` 直接写流、自动补零，代码更短也更好读。`localtime_s` / `localtime_r`
则避免了共享静态 `tm` 的线程安全问题。

### 4.2 异常体系（Exception）

```
std::runtime_error
  └── RosException
        ├── NodeException
        ├── TopicException
        └── MessageException
```

三个子类在构造函数里给 `what()` 加上固定前缀：

```cpp
explicit NodeException(const std::string& message)
    : RosException("[NodeException] " + message) {}
```

这样日志里直接 `e.what()` 就能打印出 `[NodeException] 节点名不能为空……`，不需要调用方
再拼类型名，也让控制台输出一眼能看出异常类别。

### 4.3 日志（Logger）

`Logger` 全部是静态接口，内部持有级别阈值与一个 `std::ofstream`：

```cpp
void Logger::write(LogLevel level, const std::string& module, const std::string& message) {
    if (static_cast<int>(level) < static_cast<int>(minLevel_)) return;   // 级别过滤
    ...
    std::cout << line << std::endl;
    if (file_.is_open()) file_ << line << std::endl;                     // 同时落盘
}
```

统一格式：`[级别] [时间戳] [模块名] 内容`，例如：

```
[INFO ] [2026-11-11 21:44:22] [pub_temp] 发布消息 → 话题=sensor 内容="temperature=25.3"
```

**收益**：后续要加「写入文件」「按级别过滤」「加颜色」等功能，只改这一个类，
不需要动十几个业务文件。这也是需求 FR-15（日志分级与持久化）的实现。

### 4.4 消息（Message）

```cpp
Message::Message(std::string content)
    : content_(trim(content)),
      timestamp_(nowTimestamp()) {
    if (content_.empty()) {
        throw MessageException("消息内容不能为空：内容长度为 0");
    }
}
```

两个要点：

1. **先 trim 再判空**，否则传入 `"   "` 这种纯空白会被当成合法内容；
2. 时间戳在**初始化列表**里生成，早于函数体，保证「对象一旦构造成功，时间戳必然存在」；
   头文件中只暴露 `content()` 与 `timestamp()` 两个 `const` getter，不提供任何 setter，
   从接口层面保证不可变。

### 4.5 节点（Node）

节点基类承担三件事：名称校验、状态管理、析构反注册。

```cpp
Node::~Node() {
    ROS::instance().unregister(this);   // 关键：防止核心持有悬空指针
}

void Node::ensureActive(const char* action) const {
    if (!initialized_) throw NodeException("节点尚未初始化，无法执行 " + std::string(action) + ...);
    if (closed_) {
        Logger::warn(name_, std::string("节点已关闭，拒绝执行 ") + action);
        throw NodeException("节点已关闭，无法执行 " + std::string(action));
    }
}
```

**注意析构函数里的调用不能抛异常**——如果 `unregister` 抛出，析构过程中异常逃逸会导致
`std::terminate()` 直接终止进程。因此 `ROS::unregister` 被声明为 `noexcept`，且对
「找不到该节点」的情况直接返回（幂等），不报错。

### 4.6 发布者与订阅者

两者的结构和行为几乎对称，都是「init 注册 → 业务动作 → shutdown 记录」：

```cpp
void Publisher::init() {
    if (isInitialized()) throw NodeException("节点 \"" + name_ + "\" 重复初始化");
    ROS::instance().registerPublisher(this);   // 失败会抛异常，此时状态位尚未修改
    markInitialized();
    Logger::info(name_, "发布者已初始化，话题=" + topic_);
}

void Publisher::publish(const std::string& sensorData) {
    ensureActive("发布消息");
    const Message message(sensorData);          // 空内容在此抛出 MessageException
    Logger::info(name_, "发布消息 → 话题=" + topic_ + " 内容=\"" + message.content() + "\"");
    ROS::instance().publish(topic_, message);   // 不等待、不感知订阅者
}
```

**为什么先注册再置状态位**：如果注册因重名失败而抛出，节点仍应处于「未初始化」状态，
这样调用方可以修正后重试。若先置位再注册，异常后节点会变成「已初始化但没注册」的
不一致状态。

### 4.7 核心管理（ROS）

单例用 Meyers 写法：

```cpp
ROS& ROS::instance() {
    static ROS instance;   // C++11 起保证线程安全的局部静态初始化
    return instance;
}
```

拷贝构造与赋值被 `= delete`，构造函数私有，因此无法伪造第二个实例。

转发是核心逻辑，一个循环即可：

```cpp
const auto it = subscribers_.find(topic);
if (it == subscribers_.end() || it->second.empty()) {
    throw TopicException("话题不存在：\"" + topic + "\" 尚未注册任何订阅者");
}
for (Subscriber* subscriber : it->second) {
    subscriber->receive(message);
}
```

注销接口用到 `remove_if` + 基类指针比较：

```cpp
list.erase(std::remove_if(list.begin(), list.end(),
                          [node](Publisher* item) { return static_cast<Node*>(item) == node; }),
           list.end());
```

**为什么不写 `dynamic_cast<Publisher*>(node)`**：传进来的是 `Node*`，具体类型未知，
向下转型是危险动作；而 `Publisher*` 向上转成 `Node*` 是合法且零开销的，直接比地址即可。

统一关闭必须「先遍历、后清空」：

```cpp
for (Node* node : nodes_) { ... node->shutdown(); }   // 先遍历
publishers_.clear(); subscribers_.clear(); nodes_.clear();   // 后清空
```

若边遍历边 `clear`，迭代器立即失效，是最常见的崩溃写法。

## 5 踩坑记录

这一节记录开发过程中真实遇到的问题，也是最容易在答辩时被问到的地方。

### 5.1 中文全部乱码（三层原因叠加）

| 层次 | 现象 | 解决办法 |
|---|---|---|
| 源文件 | VS 默认按系统 ANSI(GBK) 保存，中文在 UTF-8 编译器下变乱码 | `.editorconfig` 指定 `charset = utf-8-bom`，统一存为 UTF-8 |
| 编译期 | MSVC 按 GBK 解析无 BOM 的源文件 | `CMakeLists.txt` 加 `/utf-8`，强制源码与执行字符集都是 UTF-8 |
| 运行期 | 控制台代码页是 936，UTF-8 字节被按 GBK 显示 | `main` 中调用 `SetConsoleOutputCP(CP_UTF8)` |

三层缺一层都会乱码，这也是为什么第 3 层必须写在 `main` 里而不是靠系统设置。

### 5.2 `CMake Error: Cannot find source file`

先写 `CMakeLists.txt`、后创建 `src/main.cpp` 时，配置阶段直接失败，报
`no buildsystem generated`。原因很直白：`add_executable` 引用的文件必须已存在。
教训是**先有文件、再写构建脚本**，或者至少同时创建。

### 5.3 VS 里 47 个「找不到头文件」的假错误

命令行重新执行过 CMake 后，VS 的 IntelliSense 数据库仍是旧的，`#include "rosmini/..."`
全被标红，但实际编译完全通过。解决办法：修改 `CMakeLists.txt` 触发重新配置，
或使用菜单「项目 → 删除缓存并重新配置」。**判断真假错误的依据是编译结果，不是波浪线。**

### 5.4 行尾符造成的「整份文件都被修改」

`core.autocrlf = true` 时，工作区是 CRLF、仓库内是 LF，编辑器保存一次就可能让 Git 认为
每行都变了。最终把 `.editorconfig` 的 `end_of_line` 统一为 `lf`，并关闭该仓库的
`core.autocrlf`，`git diff` 才稳定下来。

### 5.5 析构函数里抛异常 = 程序终止

最初 `unregister` 在「找不到节点」时抛异常，导致节点析构时若已被 `shutdownAll` 清理过，
就会在析构路径上抛出异常，触发 `std::terminate()`。改为 `noexcept` + 幂等返回后解决。

## 6 设计取舍

| 决策点 | 选择 | 备选 | 理由 |
|---|---|---|---|
| 单例实现 | Meyers 局部静态 | 全局变量 / `new` + 指针 | 线程安全、自动释放、无法被拷贝 |
| 节点所有权 | 裸指针 + 析构反注册 | `unique_ptr` / `shared_ptr` | 节点由调用方创建（栈对象），核心只借用；`unique_ptr` 会夺走所有权，与语义冲突 |
| 映射结构 | 两张 `unordered_map<string, vector<T*>>` | 单表存 `Node*` + 运行时判断 | 分表后转发只查订阅表，且无需 `dynamic_cast` |
| 错误处理 | 自定义异常 | 返回错误码 | 返回值容易被忽略；异常无法被静默跳过，且能携带上下文 |
| 时间戳 | `std::put_time` | `strftime` | 免缓冲区管理、自动补零、配合 `localtime_s` 线程安全 |
| 分发方式 | 单线程同步遍历 | 队列 + 工作线程 | 当前「异步」指发布者与订阅者解耦，非多线程；同步实现更易测试与演示 |
| 日志 | 统一 `Logger` | 各处直接 `cout` | 加分项要改文件输出与分级，集中后只改一处 |

## 7 复杂度分析

| 操作 | 时间复杂度 | 说明 |
|---|---|---|
| 注册节点 | 平均 O(1)（查重 O(n)） | `unordered_map` 插入；查重需遍历节点总表，规模小可接受 |
| 按话题转发 | 平均 O(1) + O(k) | k 为该话题订阅者数量 |
| 统一关闭 | O(n) | n 为节点总数 |
| 注销节点 | O(n + m) | 需扫描两张表与总表，节点数很小 |

若节点规模扩大到数千级，可把查重改为维护一个 `unordered_set<string>` 名字集合，
把注册降为严格 O(1)；当前规模没有必要。

## 8 已知限制

1. **单线程**：多线程并发发布不安全，未加锁；
2. **消息仅支持字符串**：结构化数据需扩展（加分项 `SensorMessage`）；
3. **无持久化消息**：进程退出后消息不保留，仅日志落盘；
4. **同一话题允许重复订阅**：同一节点对象不会被注册两次，但不阻止两次创建同名话题订阅者。
